## Панель управления теплицей (front)

Внешний вид страницы сделан на чистом HTML/CSS/JS — без React и без сборщиков.

```
front/
  index.html                    разметка панели (шапка, навигация, 8 разделов, экран входа)
  css/main.css                  тема оформления: светлая/тёмная, адаптивная сетка
  js/app.js                     роутер разделов, отрисовка данных, графики, вход в аккаунт
  TriEblanaiPraktika/index.html служебная страница без ссылок в интерфейсе
```

### Как запустить

**Вариант 1 — просто открыть файл.** Двойной клик по `front/index.html`.
Пути к CSS и JS относительные, поэтому всё подключается и по `file://`.
В этом случае панель работает в демонстрационном режиме (данные генерируются в браузере).

**Вариант 2 — Live Server в VS Code.** ПКМ по `front/index.html` → *Open with Live Server*.

**Вариант 3 — статический сервер из Python.**
```powershell
py -m http.server 5500 --directory front
```
Затем открыть http://127.0.0.1:5500/

### Что умеет панель

- Разделы: Панель, Влага, Свет, Полив, Проветривание, Режим, Журнал (переключение через hash-навигацию).
- Показатели температуры, влажности почвы, освещённости и уровня воды с графиками и спарклайнами.
- Переключатели исполнителей (полив, проветривание, досветка), ручной запуск на заданное время.
- Настройка целевой влажности, порогов и длительностей; режимы Авто / Эко / Интенсив / Ручной.
- Журнал событий с фильтрами, экспорт данных в JSON, сброс настроек.
- Светлая и тёмная тема, состояние сохраняется в `localStorage`.
- Вход в аккаунт: панель помнит прошлые настройки за пользователем (см. раздел
  «Аккаунты и вход в панель»). Пока сервера нет, есть режим «Без входа».

### Связь с бэкендом

Фронтенд ожидает `GET /api/state` и принимает JSON вида:

```json
{
  "sensors": { "temperature": 24.5, "moisture": 48, "light": 12400 },
  "tank": 78,
  "devices": { "watering": { "on": false }, "ventilation": { "on": false } }
}
```

Адрес API задаётся в разделе «Режим». Пока эндпоинт не реализован, панель
показывает статус «Автономный режим» и работает на демонстрационных данных.

## Что нового: 12 участков, бэкенд с БД, Arduino и мобильное приложение

### 1. Теплица из 12 участков

Парник разделён на **12 участков** (ячеек кассеты). У каждого участка — свои
показания (температура, влажность почвы, освещённость) и свои исполнители:

* **полив** — отдельный насос на каждый участок;
* **проветривание** — вентилятор (общий/групповой);
* **досветка** — фитолампа с ШИМ.

В панели появился раздел **«Участки · 12»**: 12 карточек с микроклиматом,
статусом (норма / сухо / перегрев / мало света) и кнопками управления.
Есть сводка «сколько участков в норме / требуют полива / перегрев» и график
влажности по всем 12 участкам.

### 2. Бэкенд с базой данных

Backend — на стандартной библиотеке Python (`http.server`) + **SQLite**.
Для работы сервера внешние зависимости не нужны; для режима PostgreSQL
достаточно одного драйвера `psycopg` (см. ниже).

```
backend/
  server.py                REST API, автоматика, раздача PWA и статики front/
  db.py                    схема БД и запросы, выбор бэкенда (open_database)
  db_postgres.py           тот же слой доступа, но для PostgreSQL
  schema_postgres.sql      DDL для PostgreSQL (можно выполнить в pgAdmin)
  migrate_to_postgres.py   перенос данных из SQLite в PostgreSQL
  arduino.py               канал связи с Arduino + встроенный эмулятор датчиков
  auth.py                  пароли (PBKDF2-SHA256), токены сессий, проверки логина
```

Таблицы: `zones` (12 участков), `readings` (история показаний),
`zone_devices` (исполнители по участкам), `settings` (пороги и режим),
`state` (бак, форточка, источник данных), `logs` (журнал событий),
`users` (аккаунты панели), `auth_sessions` (выданные токены входа),
`user_states` (сохранённое состояние панели по пользователям),
`secret_data` (данные служебной страницы).

#### Запуск

```powershell
# из корня проекта
py backend/server.py                     # эмулятор датчиков, http://127.0.0.1:8000
py backend/server.py --port 8000 --open  # открыть панель в браузере
py backend/server.py --serial COM3       # работа с реальной Arduino
py backend/server.py --no-simulator      # требовать плату (эмулятор запрещён)
py backend/server.py --host 0.0.0.0 --token "длинный-секрет"   # доступ по сети только с ключом
```

Сервер сам закрывает **все** запросы панели: и API, и статику, поэтому
фронтенд открывается по адресу сервера.

#### API-ключ

Если сервер доступен по сети (`--host 0.0.0.0`) или опубликован в интернет,
задайте ключ — ключом `--token` или переменной `GREENHOUSE_TOKEN`. Тогда все
запросы `/api/*` требуют заголовок `X-Api-Token` (либо параметр `?token=...`)
и без него возвращают `401`:

```powershell
$env:GREENHOUSE_TOKEN = "длинный-секрет"
py backend/server.py --host 0.0.0.0
curl -H "X-Api-Token: длинный-секрет" http://127.0.0.1:8000/api/state
```

В панели ключ вводится в поле **«API-ключ»** на вкладке «Подключение к серверу»
и уходит в том же заголовке. **Без ключа** сервер работает как прежде —
поведение локального режима не меняется.

#### Аккаунты, регистрация и гостевой режим

Панель закрыта входом: логин и пароль, аккаунты — в таблице `users`
(пароли хранятся как `PBKDF2-SHA256`, 200 000 итераций, своя соль у каждого).

**Регистрация свободная** — на экране входа есть кнопка «Создать аккаунт».
Любой может завести себе аккаунт с ролью «user»; сессия открывается сразу,
повторно входить не нужно. Роль «admin» самому себе выдать нельзя.

Чтобы не перебирали пароли, вход и регистрация ограничены: не больше
10 попыток в минуту с одного адреса (дальше `429`).

При **самом первом запуске** дополнительно создаётся администратор `admin`,
а пароль сервер печатает в консоль один раз:

```
Создан администратор «admin». Пароль: <случайный пароль>
Смените пароль после входа или задайте GREENHOUSE_ADMIN_PASSWORD до первого запуска.
```

Чтобы не запоминать случайный пароль, задайте свой заранее:

```powershell
$env:GREENHOUSE_ADMIN_PASSWORD = "свой-пароль"   # только для первого запуска
py backend/server.py
```

Дальше аккаунты создаются на служебной странице (см. ниже) или регистрацией
в самой панели. Вход даёт токен (заголовок `Authorization: Bearer <токен>`,
срок жизни 30 дней).

Что даёт вход:

- **панель помнит прошлое состояние** — режим, пороги, тему, длительности и
  открытый раздел сохраняются за пользователем в `user_states` и
  восстанавливаются при следующем входе, даже в другом браузере;
- изменения порогов и режима сразу уходят в `/api/settings` и `/api/mode`,
  то есть влияют на саму теплицу, а не только на ваш браузер;
- открыто управление теплицей (без входа оно закрыто).

**Гостевой режим.** Кнопка «Без входа» пускает в панель без аккаунта. Тогда
данные датчиков видно, но **управление закрыто**: переключатели полива,
проветривания и досветки, смена режима и пороги недоступны, а сверху висит
напоминание с кнопками «Зарегистрироваться» и «Войти». Вошедшему блокировка
не мешает; остановка исполнителя по таймеру не блокируется — иначе насос мог бы
остаться включённым, если выйти из аккаунта во время полива.

Без сервера панель, как и раньше, работает в демонстрационном режиме: требовать
вход там не за что, поэтому ограничения не включаются, а всё хранится только
в `localStorage`.

Разделы `/api/auth/*`, `/api/admin/*` и `/api/secret/*` защищены паролем
пользователя, а не общим API-ключом: иначе войти было бы невозможно.

#### Служебная страница /TriEblanaiPraktika

Секретная страница без ссылок в интерфейсе — адрес
`http://127.0.0.1:8000/TriEblanaiPraktika` (та же страница лежит в
`front/TriEblanaiPraktika/index.html` и на хостинге открывается по
`/TriEblanaiPraktika/`). Она предназначена для служебных данных теплицы.

- **просмотр** записей доступен всем, кто знает адрес;
- **изменения** (записи и аккаунты) — только администратору: страница
  спрашивает логин и пароль и работает с `Bearer`-токеном;
- таблица «Данные страницы» пока пустая и готова к наполнению: запись — это
  пара «название → значение», одинаковые названия перезаписываются.

#### REST API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | состояние сервиса и канала данных |
| GET | `/api/state` | полное состояние: 12 участков + агрегаты |
| GET | `/api/zones` | список участков |
| GET | `/api/zones/<id>` | один участок |
| GET | `/api/zones/<id>/history?limit=60` | история показаний участка |
| GET | `/api/history?zone_id=&limit=` | история (все или один участок) |
| GET | `/api/logs?limit=&level=` | журнал событий |
| GET | `/api/settings` | глобальные настройки и пороги |
| GET | `/api/arduino` | статус связи с платой |
| POST | `/api/devices` | `{"zone_id":1,"device":"watering","on":true,"seconds":10}` |
| POST | `/api/settings` | изменить пороги/режим |
| POST | `/api/mode` | `{"mode":"auto\|eco\|boost\|manual"}` |
| POST | `/api/logs/clear` | очистить журнал |
| POST | `/api/auth/login` | `{"username":"...","password":"..."}` → токен и сохранённое состояние |
| POST | `/api/auth/register` | свободная регистрация: `{"username":"...","password":"..."}` → токен, роль «user» |
| POST | `/api/auth/logout` | завершить сессию (Bearer) |
| GET | `/api/auth/me` | текущий пользователь (Bearer) |
| GET | `/api/auth/state` | сохранённое состояние панели (Bearer) |
| POST | `/api/auth/state` | сохранить состояние панели (Bearer) |
| POST | `/api/auth/password` | `{"current":"...","new":"..."}` — смена пароля (Bearer) |
| GET | `/api/admin/users` | список аккаунтов (только `admin`) |
| POST | `/api/admin/users` | `{"username":"...","password":"...","role":"user"}` (только `admin`) |
| POST | `/api/admin/users/<id>/password` | `{"new":"..."}` — сброс пароля (только `admin`) |
| DELETE | `/api/admin/users/<id>` | удалить аккаунт (только `admin`) |
| GET | `/api/secret/data` | записи служебной страницы |
| POST | `/api/secret/data` | `{"name":"...","value":"..."}` (только `admin`) |
| DELETE | `/api/secret/data/<id>` | удалить запись (только `admin`) |

`zone_id = 0` в `POST /api/devices` — команда сразу всем 12 участкам.
Логин одновременно является и паролем: `X-Api-Token` нужен для «теплицы»,
`Authorization: Bearer` — для аккаунта. Их можно использовать вместе.

При заданном API-ключе любой из методов ниже требует заголовок
`X-Api-Token` (или `?token=...`), иначе вернётся `401`.

Пример:

```powershell
curl http://127.0.0.1:8000/api/state
curl -X POST http://127.0.0.1:8000/api/devices -H "Content-Type: application/json" -d "{\"zone_id\":3,\"device\":\"watering\",\"on\":true,\"seconds\":10}"
```

#### PostgreSQL и pgAdmin

Тот же сервер и тот же REST API умеют работать с **PostgreSQL** вместо файла
SQLite: состав таблиц и все запросы совпадают, но время хранится в `TIMESTAMPTZ`,
флаги — в `BOOLEAN`, а ключи — в `BIGSERIAL`. Ответы API при этом не меняются.

```powershell
# 1) драйвер (нужен только для режима PostgreSQL)
py -m pip install -r backend/requirements.txt

# 2) база и роль — один раз, из psql или pgAdmin → Query Tool
#    CREATE ROLE greenhouse LOGIN CREATEDB PASSWORD 'пароль';
#    CREATE DATABASE greenhouse OWNER greenhouse;

# 3) чтобы не вводить пароль каждый раз — строка в %APPDATA%\postgresql\pgpass.conf
#    localhost:5432:*:greenhouse:пароль
#    (формат: хост:порт:база:роль:пароль, * — любая база)

# 4) сервер на PostgreSQL
py backend/server.py --dsn "postgresql://greenhouse@localhost:5432/greenhouse"

# либо через переменную окружения, чтобы не указывать ключ каждый раз
$env:GREENHOUSE_DSN = "postgresql://greenhouse@localhost:5432/greenhouse"
py backend/server.py
```

Без `--dsn` (и без `GREENHOUSE_DSN`) сервер по-прежнему пишет в SQLite —
ничего переписывать не нужно. Пароль не хранится ни в репозитории, ни в командах:
его подхватывает `pgpass.conf` (если файла нет, сервер спросит пароль).

Схема создаётся автоматически при первом запуске, вручную её можно выполнить
из файла [`backend/schema_postgres.sql`](backend/schema_postgres.sql).

**Перенос уже накопленных данных из SQLite:**

```powershell
py backend/migrate_to_postgres.py --dsn "postgresql://greenhouse@localhost:5432/greenhouse"
py backend/migrate_to_postgres.py --dsn "..." --replace               # сначала очистить таблицы в PostgreSQL
py backend/migrate_to_postgres.py --dsn "..." --history-limit 5000    # только свежие показания
```

Скрипт копирует `zones`, `readings`, `zone_devices`, `settings`, `state`, `logs`
и повторный запуск можно делать без опаски — строки обновляются по ключу.

**Просмотр в pgAdmin:**

1. Правый клик на **Servers** → **Register → Server…**
2. Вкладка *General*: Name — «Теплица».
3. Вкладка *Connection*: Host — `localhost`, Port — `5432`,
   Maintenance database — `greenhouse`, Username — `greenhouse`, пароль роли
   (галочка *Save password* — чтобы не вводить каждый раз).
4. **Save** → `Databases → greenhouse → Schemas → public → Tables`.
5. Правый клик на таблице → **View/Edit Data → All Rows**.

Те же подключения можно загрузить разом из файла
[`pgadmin-servers.json`](pgadmin-servers.json): **File → Import Servers…** →
указать файл → **Import**.

**Чтобы добавить ещё одну базу или таблицу:**

* новая база — `CREATE DATABASE имя OWNER greenhouse;` и запуск сервера с её DSN;
* новая таблица — добавить операторы `CREATE TABLE` в
  [`backend/schema_postgres.sql`](backend/schema_postgres.sql), соответствующие
  запросы в [`backend/db_postgres.py`](backend/db_postgres.py) и (если нужно
  переносить данные) строку в `TRANSFERS` там же.

### 3. Датчики через Arduino

Прошивка: [`hardware/arduino/greenhouse_12zone/greenhouse_12zone.ino`](hardware/arduino/greenhouse_12zone/greenhouse_12zone.ino)

* 12 датчиков влажности через аналоговый мультиплексор **CD74HC4067**;
* температура/влажность воздуха — **DHT22**;
* уровень воды в баке — **HC-SR04**;
* управление — 2× **74HC595** (12 насосов + вентилятор + фитолампа).

Обмен — построчный JSON по Serial (115200 бод). Схема соединений и список
библиотек — в [`hardware/README.md`](hardware/README.md).

**Платы пока нет — это не проблема.** Если не указан `--serial`, сервер
включает встроенный **эмулятор**: физическая модель микроклимата 12 участков
(испарение, полив, нагрев, освещение от времени суток). Эмулятор полностью
повторяет протокол платы, поэтому переход на реальное железо сводится к
добавлению флага `--serial COM3`.

### 4. Мобильное приложение (PWA)

Панель — это **Progressive Web App**: её можно установить на телефон как
обычное приложение (иконка на экране, полноэкранный режим, офлайн-оболочка).

```
front/
  index.html             разметка панели
  css/, js/              стили и логика
  manifest.webmanifest   манифест PWA (иконки, тема, ярлыки)
  service-worker.js      кэш оболочки, офлайн-режим
  .htaccess              тип содержимого манифеста и заголовки кэша для хостинга
  icons/                 иконки 192/512 + maskable
```

* На Android (Chrome): меню → **«Установить приложение»** либо кнопка **⬇** в шапке.
* На iOS (Safari): **«Поделиться» → «На экран «Домой»»**.

Кнопка **⬇** в шапке появляется, когда браузер готов установить приложение.
Логика датчиков/API работает и офлайн (демо-режим), а при подключении к
серверу панель обновляется каждые 2 секунды.

### 5. Запуск целиком

```powershell
# 1) сервер (он же раздаёт панель и PWA)
py backend/server.py --open

#    или сразу на PostgreSQL (пароль берётся из pgpass.conf)
py backend/server.py --dsn "postgresql://greenhouse@localhost:5432/greenhouse" --open

# 2) на телефоне открыть http://<IP-компьютера>:8000/ и установить приложение
```

Для доступа с телефона запустите сервер с `--host 0.0.0.0` и откройте адрес
компьютера в локальной сети.

### 6. Публикация: панель на reg.ru, API и база — дома

Проверено по официальной документации reg.ru (help.reg.ru и приложение к оферте):
на shared-хостинге с ISPmanager **есть только MySQL, PostgreSQL нет**;
Python работает лишь как WSGI-приложение под Passenger (`passenger_wsgi.py`),
а суточный лимит CPU — 2,5–13 %, за превышение хостинг блокируется.
Поэтому бэкенд теплицы — с COM-портом Arduino, циклом автоматики и PostgreSQL —
остаётся на домашнем ПК, а на хостинг уезжает только статичная панель:

```
front/   →  https://ваш-домен.ru        (FTP 21 или SFTP 22, корень сайта)
backend  →  домашний ПК: PostgreSQL + Arduino, наружу через HTTPS-туннель
```

Порядок:

1. Загрузить содержимое папки `front/` в корень сайта
   (`/var/www/uXXXXXXX/data/www/<домен>/`): `index.html`, `css/`, `js/`,
   `icons/`, `manifest.webmanifest`, `service-worker.js`,
   `TriEblanaiPraktika/` (служебная страница).
   Панель должна лежать в корне — иначе service worker не получит нужную область
   видимости и приложение не установится.
2. В ISPmanager включить бесплатный **Let's Encrypt** и редирект HTTP→HTTPS.
3. Поднять туннель к домашнему серверу — его выдаёт Cloudflare Tunnel.
   Проще всего скриптом [`_run_public.ps1`](_run_public.ps1), он поднимает
   и сервер, и туннель, и печатает готовый адрес:

   ```powershell
   $env:GREENHOUSE_TOKEN = "длинный-секрет"          # ключ панели, обязателен
   $env:GREENHOUSE_DSN   = "postgresql://greenhouse@localhost:5432/greenhouse"
   $env:GREENHOUSE_ADMIN_PASSWORD = "пароль-админа"  # только для первого запуска
   powershell -ExecutionPolicy Bypass -File _run_public.ps1
   ```
   `GREENHOUSE_ADMIN_PASSWORD` нужен лишь один раз: пока в базе нет ни одного
   аккаунта, сервер создаёт `admin` с этим паролем. Без переменной пароль
   генерируется случайным и печатается в окне сервера — не пропустите его.

   Скрипт требует `cloudflared` (`winget install Cloudflare.cloudflared`),
   сохраняет адрес туннеля в `data/tunnel-url.txt` и печатает команду остановки.
   Туннель запускается в режиме `--protocol http2`: QUIC(UDP) часто режется
   домашним антивирусом или файрволом.
4. В панели на вкладке «Режим» → «Подключение к серверу» указать **Адрес API**
   (адрес из `data/tunnel-url.txt`) и **API-ключ**, нажать «Подключиться»,
   после чего войти в аккаунт (логин `admin` и пароль из шага 3).

**Постоянный адрес.** Быстрый туннель без аккаунта Cloudflare каждый раз получает
новое имя вида `https://<случайное-имя>.trycloudflare.com`, поэтому после
перезапуска адрес в панели нужно менять. Постоянный адрес даёт **именованный
туннель**, но для него домен должен быть переведён на NS-серверы Cloudflare
(на reg.ru это смена NS в личном кабинете, DNS-зону придётся перенести) — это
самостоятельный шаг, который лучше делать осознанно. CNAME `api.ai-parnik.ru`
на быстрый туннель не поможет: Cloudflare отвечает только на своё случайное имя.

**Демонстрация «здесь и сейчас»:** пока домашний ПК включён и запущен
`_run_public.ps1`, панель на `ai-parnik.ru` полностью рабочая. Как только ПК
выключается, панель переходит в демо-режим — данные в ней становятся местной
симуляцией, а не показаниями теплицы.

Ограничения, о которых стоит помнить:

* адрес API обязан быть **https** — иначе браузер заблокирует запросы
  как mixed content (на http-сайте панель останется в демо-режиме);
* **без API-ключа публиковать сервер нельзя** — команды насосам и вентиляции
  сможет отдать любой, кто узнает адрес;
* **панель закрыта входом**, а служебная страница `/TriEblanaiPraktika` видна
  всем, кто знает её адрес (изменения в ней — только под администратором);
* пока домашний ПК выключен, панель работает в демо-режиме;
* ключ панель хранит в `localStorage` браузера, поэтому на чужом устройстве
  его лучше не вводить. Токен входа тоже лежит в `localStorage` — на общем
  компьютере выходите из аккаунта кнопкой **⎋**.

#### Обновление панели на хостинге

nginx отдаёт `.js` и `.css` с кэшем на 45 дней, а `.html` и `.webmanifest` — через
Apache. Поэтому заголовки задаёт файл [`front/.htaccess`](front/.htaccess): он
добавляет манифесту тип `application/manifest+json` (без него браузер не
предложит установку и не включит приложение) и запрещает кэшировать сам HTML.

Скрипты и стили идут мимо `.htaccess`, поэтому их ссылки версионируются:
`css/main.css?v=N` и `js/app.js?v=N` в [`front/index.html`](front/index.html),
то же `N` в `ASSET_VERSION` в [`front/js/app.js`](front/js/app.js) и в `VERSION`
в [`front/service-worker.js`](front/service-worker.js). При выпуске новой версии
поднимите `N` в этих трёх файлах и загрузите файлы заново — обновление дойдёт
и до тех, у кого панель уже установлена.
