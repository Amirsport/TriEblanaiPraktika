## Панель управления теплицей (front)

Внешний вид страницы сделан на чистом HTML/CSS/JS — без React и без сборщиков.

```
front/
  index.html                    разметка панели (шапка, навигация, 8 разделов, экран входа)
  css/main.css                  тема: светлая/тёмная, адаптивная сетка, зелёная и красная палитры
  js/app.js                     роутер разделов, отрисовка данных, графики, вход в аккаунт
  TriEblanaiPraktika/index.html служебная страница без ссылок в интерфейсе
  games/index.html              игровая комната — только по прямой ссылке, красная палитра
  games/narutodle/index.html    дуэль на двоих: один персонаж на двоих игроков
  games/narutodle/portraits/    свои картинки персонажей (необязательно)
  games/animesongless/index.html угадай аниме по фрагменту опенинга: соло и онлайн
  games/animesongless/audio/    свои записи опенингов (необязательно)
```

### Как запустить

**Вариант 1 — просто открыть файл.** Двойной клик по `front/index.html`.
Пути к CSS и JS относительные, поэтому всё подключается и по `file://`.
В этом случае панель работает в демонстрационном режиме (данные генерируются в браузере).

**Вариант 2 — Live Server в VS Code.** ПКМ по `front/index.html` → *Open with Live Server*.

**Вариант 3 — статический сервер из Python.**
```powershell
py -m http.server 5500 --directory front
```
Затем открыть http://127.0.0.1:5500/

### Что умеет панель

- Разделы: Панель, Влага, Свет, Полив, Проветривание, Режим, Журнал (переключение через hash-навигацию).
- Показатели температуры, влажности почвы, освещённости и уровня воды с графиками и спарклайнами.
- Переключатели исполнителей (полив, проветривание, досветка), ручной запуск на заданное время.
- Настройка целевой влажности, порогов и длительностей; режимы Авто / Эко / Интенсив / Ручной.
- Журнал событий с фильтрами, экспорт данных в JSON, сброс настроек.
- Светлая и тёмная тема, состояние сохраняется в `localStorage`.
- Вход в аккаунт: панель помнит прошлые настройки за пользователем (см. раздел
  «Аккаунты и вход в панель»). Пока сервера нет, есть режим «Без входа».

### Связь с бэкендом

Фронтенд ожидает `GET /api/state` и принимает JSON вида:

```json
{
  "sensors": { "temperature": 24.5, "moisture": 48, "light": 12400 },
  "tank": 78,
  "devices": { "watering": { "on": false }, "ventilation": { "on": false } }
}
```

Адрес API задаётся в разделе «Режим». Пока эндпоинт не реализован, панель
показывает статус «Автономный режим» и работает на демонстрационных данных.

## Что нового: 12 участков, бэкенд с БД, Arduino и мобильное приложение

### 1. Теплица из 12 участков

Парник разделён на **12 участков** (ячеек кассеты). У каждого участка — свои
показания (температура, влажность почвы, освещённость) и свои исполнители:

* **полив** — отдельный насос на каждый участок;
* **проветривание** — вентилятор (общий/групповой);
* **досветка** — фитолампа с ШИМ.

В панели появился раздел **«Участки · 12»**: 12 карточек с микроклиматом,
статусом (норма / сухо / перегрев / мало света) и кнопками управления.
Есть сводка «сколько участков в норме / требуют полива / перегрев» и график
влажности по всем 12 участкам.

### 2. Бэкенд с базой данных

Backend — на стандартной библиотеке Python (`http.server`) + **SQLite**.
Для работы сервера внешние зависимости не нужны; для режима PostgreSQL
достаточно одного драйвера `psycopg` (см. ниже).

```

  db.py                    схема БД и запросы, выбор бэкенда (open_database)
  db_postgres.py           тот же слой доступа, но для PostgreSQL
  schema_postgres.sql      DDL для PostgreSQL (можно выполнить в pgAdmin)
  migrate_to_postgres.py   перенос данных из SQLite в PostgreSQL
  arduino.py               канал связи с Arduino + встроенный эмулятор датчиков
  device_link.py           канал «сервер на VPS ↔ домашний агент»: очередь команд и приём показаний
  device_agent.py          сам агент: запускается дома рядом с платой и держит COM-порт
  auth.py                  пароли (PBKDF2-SHA256), токены сессий, проверки логина
  narutodle.py             движок дуэли: раунды, комнаты, сравнение графов
  narutodle_data.py        набор персонажей и цвета деревень (источник для базы)
  seed_narutodle.py        наполнение базы персонажами и привязка картинок
  songless.py              движок «Аниме-сонглесса»: соло-заходы и комнаты
  songless_data.py         набор опенингов (источник для базы)
  seed_songless.py         наполнение базы треками и привязка записей
  csdraft.py               движок драфт-рогаликов: драфт состава и прогон по сетке
  csdraft_data.py          составы прошлых турниров по CS (источник для базы)
  draft_games.py           реестр драфт-игр: роли, арены, стадии и правила матчей
  draft_games_data.py      составы VCT (Valorant) и RLCS (Rocket League)
  seed_csdraft.py          наполнение базы составами, просмотр и проверка набора
  raporder.py              движок «Рэп-хронологии»: раунды, комнаты, подсчёт очков
  raporder_data.py         набор треков русского рэпа (исполнитель, название, год)
  seed_raporder.py         наполнение базы треками, правка годов и проверка набора
  dotadraft.py             движок «322-0»: бюджет состава, герои по позициям, стадии
  dotadraft_data.py        пул игроков Streamers Battle 13 и герои Dota 2
  seed_dotadraft.py        наполнение базы пулом 322-0, правка цен и проверка набора
  songguess.py             движок «Угадай песню»: темы, таймер, очки, разбор
  songguess_data.py        126 песен трёх тем (аниме, русский рэп, хип-хоп)
  seed_songguess.py        привязка записей к песням (файлы или ссылки), проверка набора
```

Таблицы: `zones` (12 участков), `readings` (история показаний),
`zone_devices` (исполнители по участкам), `settings` (пороги и режим),
`state` (бак, форточка, источник данных), `logs` (журнал событий),
`users` (аккаунты панели), `auth_sessions` (выданные токены входа),
`user_states` (сохранённое состояние панели по пользователям),
`secret_data` (данные служебной страницы), `narutodle_characters` (персонажи
дуэли: графы, цвет, картинка), `narutodle_matches` (журнал партий Narutodle),
`songless_tracks` (треки «Аниме-сонглесса»: сведения и запись к ним),
`csdraft_packs` (паки драфт-игр: карты, игроки и колонка `game` — какая игра),
`csdraft_runs` (журнал прогонов драфтов: кто играл, каким составом и чем кончилось),
`raporder_tracks` (треки «Рэп-хронологии»: исполнитель, название, год),
`raporder_matches` (журнал партий «Рэп-хронологии»: режим, счёт, победитель),
`dotadraft_players` (пул «322-0»: ник и стоимость в очках),
`dotadraft_heroes` (герои «322-0»: имя, позиция 1–5 и игровая оценка),
`songguess_tracks` (песни «Угадай песню»: тема, исполнитель, год и запись к ним),
`songguess_runs` (журнал заходов «Угадай песню»: тема, таймер, счёт, разбор раундов),
`device_commands` (очередь команд домашнему агенту, когда сервер стоит на VPS).

Колонки, появившиеся после первых версий, сервер добавляет сам при запуске
(`ALTER TABLE`): старые базы не нужно пересоздавать — `game` в таблицах драфтов
и таблицы «Рэп-хронологии» появятся при первом запуске новой версии.

#### Запуск

```powershell
# из корня проекта
py backend/server.py                     # эмулятор датчиков, http://127.0.0.1:8000
py backend/server.py --port 8000 --open  # открыть панель в браузере
py backend/server.py --serial COM3       # работа с реальной Arduino
py backend/server.py --no-simulator      # требовать плату (эмулятор запрещён)
py backend/server.py --host 0.0.0.0 --token "длинный-секрет"   # доступ по сети только с ключом
```

Сервер сам закрывает **все** запросы панели: и API, и статику, поэтому
фронтенд открывается по адресу сервера.

Нужен **Python 3.11 или новее** — поддерживаются 3.11, 3.12 и 3.13; на 3.9 и
3.10 проект больше не рассчитан. Сервер и игры работают на стандартной
библиотеке, поэтому для запуска ничего устанавливать не нужно; сторонние пакеты
есть только для режима PostgreSQL, связи с реальной платой и служебных скриптов
выгрузки (см. [`backend/requirements.txt`](backend/requirements.txt)).

#### API-ключ

Если сервер доступен по сети (`--host 0.0.0.0`) или опубликован в интернет,
задайте ключ — ключом `--token` или переменной `GREENHOUSE_TOKEN`. Тогда все
запросы `/api/*` требуют заголовок `X-Api-Token` (либо параметр `?token=...`)
и без него возвращают `401`:

```powershell
$env:GREENHOUSE_TOKEN = "длинный-секрет"
py backend/server.py --host 0.0.0.0
curl -H "X-Api-Token: длинный-секрет" http://127.0.0.1:8000/api/state
```

В панели ключ вводится в поле **«API-ключ»** на вкладке «Подключение к серверу»
и уходит в том же заголовке. Если владелец сайта публикует ключ в
`games/api-address.json` (см. «Текущий адрес API на сайте»), панель и витрина
подставляют его сами — вводить руками нужно только на своей машине.
**Без ключа** сервер работает как прежде — поведение локального режима не
меняется.

Ключ закрывает данные теплицы (`/api/state`, `/api/zones`, команды исполнителям).
Разделы `/api/auth/*` и `/api/games/*` живут по аккаунту и работают без ключа:
иначе войти было бы невозможно, а ссылку-приглашение на игру пришлось бы
отправлять вместе с секретом.

#### Аккаунты, регистрация и гостевой режим

Панель закрыта входом: логин и пароль, аккаунты — в таблице `users`
(пароли хранятся как `PBKDF2-SHA256`, 200 000 итераций, своя соль у каждого).

**Регистрация свободная.** Новый посетитель видит экран входа сразу в режиме
регистрации — искать кнопку «Создать аккаунт» внизу не нужно; переключиться
на вход в существующий аккаунт можно ссылкой под кнопками.
Любой может завести себе аккаунт с ролью «user»; сессия открывается сразу,
повторно входить не нужно. Роль «admin» самому себе выдать нельзя.

Аккаунт появляется в таблице `users` в момент регистрации — и с панели, и со
служебной страницы. Посмотреть список можно на служебной странице (раздел
«Аккаунты») или запросом `SELECT id, username, role, created_at FROM users`.

Если панель открыта по адресу, где нет API теплицы (например, на хостинге без
туннеля к домашнему серверу), экран входа прямо говорит об этом вместо голого
«HTTP 404», а адрес сервера задаётся на вкладке «Режим» — вход туда открыт
кнопкой «Без входа».

Чтобы не перебирали пароли, вход и регистрация ограничены: не больше
10 попыток в минуту с одного адреса (дальше `429`).

При **самом первом запуске** дополнительно создаётся администратор `admin`,
а пароль сервер печатает в консоль один раз:

```
Создан администратор «admin». Пароль: <случайный пароль>
Смените пароль после входа или задайте GREENHOUSE_ADMIN_PASSWORD до первого запуска.
```

Чтобы не запоминать случайный пароль, задайте свой заранее:

```powershell
$env:GREENHOUSE_ADMIN_PASSWORD = "свой-пароль"   # только для первого запуска
py backend/server.py
```

Дальше аккаунты создаются на служебной странице (см. ниже) или регистрацией
в самой панели. Вход даёт токен (заголовок `Authorization: Bearer <токен>`,
срок жизни 30 дней).

Что даёт вход:

- **панель помнит прошлое состояние** — режим, пороги, тему, длительности и
  открытый раздел сохраняются за пользователем в `user_states` и
  восстанавливаются при следующем входе, даже в другом браузере;
- изменения порогов и режима сразу уходят в `/api/settings` и `/api/mode`,
  то есть влияют на саму теплицу, а не только на ваш браузер;
- открыто управление теплицей (без входа оно закрыто).

**Гостевой режим.** Кнопка «Без входа» пускает в панель без аккаунта. Тогда
данные датчиков видно, но **управление закрыто**: переключатели полива,
проветривания и досветки, смена режима и пороги недоступны, а сверху висит
напоминание с кнопками «Зарегистрироваться» и «Войти». Вошедшему блокировка
не мешает; остановка исполнителя по таймеру не блокируется — иначе насос мог бы
остаться включённым, если выйти из аккаунта во время полива.

Без сервера панель, как и раньше, работает в демонстрационном режиме: требовать
вход там не за что, поэтому ограничения не включаются, а всё хранится только
в `localStorage`.

Разделы `/api/auth/*`, `/api/admin/*` и `/api/secret/*` защищены паролем
пользователя, а не общим API-ключом: иначе войти было бы невозможно.

#### Служебная страница /TriEblanaiPraktika

Служебная консоль без ссылок в интерфейсе — адрес
`http://127.0.0.1:8000/TriEblanaiPraktika` (та же страница лежит в
`front/TriEblanaiPraktika/index.html` и на хостинге открывается по
`/TriEblanaiPraktika/`). Открывается экраном входа: нужен аккаунт панели.

- **Подключение к серверу** — адрес API теплицы с индикатором связи
  (проверка через `/api/auth/me`: ответ `200` или `401` значит, что сервер жив);
- **Аккаунты** — доступны только администратору: сводка по ролям, список,
  создание, сброс пароля и удаление; остальным показывается пояснение о правах;
- **Матчи Narutodle** — тоже только администратору: все партии дуэли из журнала
  с идентификатором, игроками и итогом (см. «Журнал матчей» ниже).

#### Страница миниигр /games

Отдельная страница `front/games/index.html`, тоже **без ссылок в интерфейсе**:
открывается только по прямому адресу `/games/` (на хостинге — там же, локально —
`http://127.0.0.1:8000/games/`). В панели и на служебной странице ссылок на неё
нет, поисковикам страница запрещена (`noindex, nofollow`).

На VPS ту же страницу раздаёт отдельный домен — витрина мини-игр: её корнем
становится `front/games`, игры открываются по коротким адресам (`/narutodle/`,
`/csdraft/`), а название сайта и запрет индексации на этом домене подменяются на
AmrGames. Если витрина заведена, раздел `/games/` на домене панели закрыт: игры
живут в одном месте (см. «Витрина игр на своём домене» в разделе про VPS).

Оформление — та же тема, что у панели ([`front/css/main.css`](front/css/main.css)),
но в красной палитре: у страницы в `<html>` стоит `data-palette="red"`, а в теме
это отдельный набор переменных рядом с зелёной палитрой теплицы. Панель и
служебная консоль остаются зелёными.

**Игры идут онлайн, поэтому связь с сервером обязательна.** В шапке — индикатор
состояния сервера и отклик в миллисекундах, в блоке «Подключение к серверу»
задаются адрес API и ключ `X-Api-Token`:

- проверка идёт запросом `GET /api/health` (ответ `401` значит «сервер жив, ключ не тот»);
- связь перепроверяется сама каждые 30 секунд, при возврате на вкладку и по кнопке;
- пока связи нет, кнопка «Играть» закрыта, а на карточке видно «нужна связь»;
- пустой адрес — обращения к тому же домену, с которого открыта страница.

Настройки подключения хранятся в `localStorage` и берутся по одной и той же
цепочке **на всех игровых страницах** (витрина `/games/`, «Аниме-сонглесс»,
Narutodle):

1. адрес из ссылки-приглашения (`?srv=…`) — он главный: комната живёт именно
   на том сервере, с которого позвали;
2. свои настройки страницы игр — `greenhouse.games.conn.v1`;
3. настройки панели теплицы — `greenhouse.state.v1` (оттуда же берётся тема);
4. `games/api-address.json` — адрес туннеля и ключ панели, которые публикует
   владелец сайта (см. «Текущий адрес API на сайте» ниже). Если своего ключа
   нет, страница берёт опубликованный, а если сервер не принял старый — заменяет
   его свежим и проверяет связь ещё раз.

Поэтому игроку не нужно ничего вводить: адрес и ключ, однажды заданные в панели
или на витрине, подхватываются и в играх. Запись сохраняется только по кнопке
«Подключиться», то есть обычный заход ничего не перезаписывает и панель
остаётся источником настроек; вместе с адресом в неё переносится и ключ панели,
чтобы он не терялся. Кнопка **«Как в панели»** на витрине возвращает настройки
панели как источник.

Если сохранённый адрес перестал отвечать (поддомен туннеля меняется при
перезапуске), игровая страница пробует по очереди всё, что знает, и берёт
живой адрес — с сообщением, откуда он взят. Панель теплицы делает то же самое
для себя: её `apiBase` меняется на опубликованный, когда сохранённый не
отвечает, поэтому игры получают свежий адрес ещё и через настройки панели.

Список игр задаётся массивом `GAMES` в конце страницы. Для каждой игры
указываются название, эмодзи-иконка, описание и адрес игры:

```js
{ id: 'ваша-игра', title: 'Название', icon: '🎮',
  description: '', href: '' }
```

Пока `description` пуст, на карточке видно «Описание появится позже»; пока пуст
`href`, кнопка неактивна — так добавляется игра, которая ещё не готова. Готовая
игра — это описание и страница рядом (например `front/games/ваша-игра/index.html`),
путь к которой указан в `href`.

##### Вторая игра: Аниме-сонглесс

`front/games/animesongless/index.html` — «угадай аниме по фрагменту опенинга».
Играется фрагмент записи, вариантов ответа четыре: верное название аниме и три
«обманки». За верный ответ даются очки, за скорость — добавка.

Два режима:

- **соло** — заход без соперников: три ошибки (или три пропуска по времени) и
  партия закончена, лучший результат хранится в браузере
  (`greenhouse.songless.best`);
- **онлайн** — комната на 2–8 человек по ссылке или коду: пять раундов на всех,
  раунд идёт одновременно, после каждого раунда видно, кто что выбрал, а в конце
  — общая таблица очков (очки, число верных ответов и потраченное время).
  Хозяин комнаты нажимает «Начать игру», когда собрались хотя бы двое.

Раунд длится 20 секунд, разбор раунда показывается 8 секунд и сменяется
следующим сам. Очки: 100 за верный ответ плюс до 60 за оставшееся время.

**Загадка не уходит в ответы API, пока раунд идёт** — ни игроку, ни зрителю:
страница получает варианты и адрес фрагмента, а название аниме узнаёт только
после разбора. Фрагмент отдаётся отдельным адресом с номером раунда
(`/api/games/songless/rooms/<код>/clip?round=N`), поэтому по имени файла аниме
тоже не угадать.

###### Записи опенингов добавляет владелец сайта

В репозитории есть **только справочные сведения** о треках (аниме, опенинг,
исполнитель, год) — сами записи защищены авторским правом, поэтому их кладёт
владелец сайта. Набор живёт в таблице `songless_tracks`, а наполняет и правит
его [`backend/seed_songless.py`](backend/seed_songless.py):

```powershell
# справочный набор в базу (SQLite — по умолчанию, PostgreSQL — с --dsn)
python backend/seed_songless.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse"

# свои записи: файлы копируются в front/games/animesongless/audio и привязываются по имени
python backend/seed_songless.py --dsn "..." --audio "C:\music" --map music.json

# или ссылкой, с точным местом фрагмента
python backend/seed_songless.py --dsn "..." --url "Наруто=https://example.org/op.mp3"
python backend/seed_songless.py --dsn "..." --start "Наруто=42" --length 10

# что в базе и что из этого можно играть
python backend/seed_songless.py --dsn "..." --list
```

Повторный запуск обновляет справочные сведения и **не затирает** привязанные
записи, начало и длину фрагмента. Куда класть файлы и что нельзя выкладывать —
в [`front/games/animesongless/audio/README.md`](front/games/animesongless/audio/README.md).

Пока в наборе меньше четырёх треков с записью, страница честно пишет, что играть
нечего, и подсказывает, куда положить файлы: синтетических «заглушек» в игре нет.

##### Первая игра: Narutodle — дуэль

`front/games/narutodle/index.html` — онлайн-дуэль на двоих. Правила простые:
на двоих загадывается **один** персонаж, у каждого своя таблица попыток, раунд
забирает тот, кто угадал первым; сдавшийся отдаёт раунд сопернику. После итога
видно ответ и ходы обоих, счёт по раундам ведётся в комнате.

**Новый раунд начинается, когда готовы оба.** Кнопка «Ещё раунд» теперь только
отмечает игрока: у нажавшего она превращается в «Ждём соперника…» и выключается,
а раунд стартует в тот момент, когда отметились оба (сервер ведёт список
готовых в `rematch`, поле `ready` в состоянии комнаты; зритель видит пометку
«готов к новому раунду»). Иначе выходило так: один уже угадывает, пока второй
дочитывает итог.

Подсказки — семь граф: пол, деревня, клан, стихии, кеккей генкай, джинчурики
и первая арка. Цвет клетки: зелёный — совпало, жёлтый — похоже (например,
у обоих есть кеккей генкай, но разный), серый — не совпало.

- **Стихии нарисованы знаками** (火 огонь, 風 ветер, 水 вода, 土 земля,
  雷 молния) на цвете стихии: так таблица читается быстрее слов, а название
  остаётся в подсказке (`title`). Если стихий несколько — значков несколько.
- **Первая арка** — место персонажа в сюжете, а не серия: список арок идёт по
  манге (Naruto главы 1–699 и Boruto), от «Страны Волн» до «Финала: Кагуя» и
  «Боруто» (константы и список `ARCS` в
  [`backend/narutodle_data.py`](backend/narutodle_data.py)). Совпадение — та же
  арка. Статус «жив/погиб» из игры убран: он выдавал ответ, а не подсказку.
  Рядом с названием арки стоит **стрелка-подсказка**: ↓ — загаданная арка раньше
  этой, ↑ — позже (сервер считает её в `compare_order`, поле `hint` в ответе).
  У совпавшей арки стрелки нет — она не нужна.
- **Разбор ответа** — ровной сеткой: по карточке на графу (подпись сверху,
  значение снизу), поэтому ничего не «пляшет» по ширине.

Имя персонажа выбирается **выпадающим списком** с портретами: начните вводить
буквы — останутся подходящие строки с аватаром и именем, выбор мышью или
стрелками с Enter, Escape закрывает список. Список открывается по вводу и по
стрелке «вниз», показывает до восьми совпадений и честно пишет, если такого
персонажа в наборе нет. Панель списка узкая и стоит по центру поля ввода,
карточки крупные — по портрету выбирать проще.

##### Персонажи: набор в базе, аватары и картинки

Набор персонажей (109 штук) лежит **в базе данных**, в таблице
`narutodle_characters`. Источник — [`backend/narutodle_data.py`](backend/narutodle_data.py)
(одна строка на персонажа), а переносится он в базу скриптом
[`backend/seed_narutodle.py`](backend/seed_narutodle.py):

```powershell
# SQLite (по умолчанию backend/greenhouse.db)
python backend/seed_narutodle.py

# PostgreSQL
python backend/seed_narutodle.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse"

# посмотреть, что уже в базе; наполнить, ничего не записывая
python backend/seed_narutodle.py --list
python backend/seed_narutodle.py --dry-run
```

Сервер читает набор из базы, а при **пустой** таблице наполняет её сам при первом
запросе к каталогу. Набор перечитывается перед каждым раундом, поэтому правки
(новый персонаж, привязанная картинка, цвет) видны без перезапуска сервера.

Повторный запуск скрипта **не стирает** уже привязанные картинки и цвета — они
обновляются только явно:

```powershell
# свои картинки: скопировать в front/games/narutodle/portraits и прописать путь
python backend/seed_narutodle.py --images "C:\my-pics" --map "Naruto=пол.название.jpg"
# или одной командой привязать/сбросить картинку у конкретного персонажа
python backend/seed_narutodle.py --url "https://example.com/photo.png" Наруто
python backend/seed_narutodle.py --clear-image Наруто
```

Если у персонажа картинка не указана, рисуется **аватар**: инициалы на цвете
деревни (`avatarHtml()`). Цвета деревень заданы в `VILLAGE_COLORS` в
[`backend/narutodle_data.py`](backend/narutodle_data.py). Куда класть свои файлы и
почему не стоит тащить в проект чужие арты — в
[`front/games/narutodle/portraits/README.md`](front/games/narutodle/portraits/README.md).

**Картинка отдаётся отдельным адресом.** В каталоге персонажей
(`GET /api/games/narutodle/characters`) вместо самого изображения стоит ссылка
`/api/games/narutodle/portrait/<id>`, а сам портрет сервер отдаёт уже картинкой с
заголовком `Cache-Control: public, max-age=86400` — браузер забирает его один раз.
Так сделано после замера: когда base64 лежал прямо в каталоге, ответ весил 3,5 МБ
и через туннель шёл больше минуты, а страница ждёт ответ 10 секунд — то есть
дуэль на сайте ai-parnik.ru просто не открывалась. Сейчас каталог — около 11 КБ
и приходит за секунду, а картинка рисуется по мере появления в списке.

Если картинка лежит файлом (`portraits/...`) или это внешняя ссылка, поле `image`
остаётся как задано, и страница берёт файл напрямую.

##### Журнал матчей

Результат каждого раунда пишется в таблицу `narutodle_matches`: **идентификатор
партии, оба игрока, число ходов, время и итог** (кто забрал раунд и кто загадан).
Запись переживает удаление аккаунта, поэтому внешнего ключа на `users` нет.

Видно их по-разному:

- **игрок** на странице игры в карточке «Мои матчи» — только свою историю
  (`GET /api/games/narutodle/matches` отдаёт матчи текущего аккаунта);
- **администратор** в служебной консоли
  `/TriEblanaiPraktika/` — панель «Матчи Narutodle» со всеми матчами
  (`GET /api/games/narutodle/matches?scope=all`), плюс счётчики матчей и
  персонажей в наборе.

Ошибка записи журнала партию не ломает: раунд заканчивается, даже если вставка
в базу не прошла.

Как играют:

1. Первый игрок открывает `/games/narutodle/`, создаёт комнату и получает код
   из четырёх символов и ссылку-приглашение;
2. второй открывает ссылку, регистрируется (или входит, если аккаунт уже есть),
   выбирает **«Играть»** и попадает в дуэль — настраивать ему по-прежнему
   ничего не нужно;
3. раунд идёт в реальном времени: страница опрашивает сервер раз в 1,2 секунды,
   поэтому чужой прогресс и итог видны без перезагрузки.

##### Наблюдение за дуэлью

Ссылка-приглашение открывает не только игру: и приглашённый, и любой
любопытствующий по ней выбирает роль — **«Играть»** или **«Смотреть»**.

- **Смотреть** — зритель видит обе таблицы попыток, кто сколько ходов сделал,
  кто забрал раунд и счёт по раундам (`GET
  /api/games/narutodle/rooms/<код>/watch`). Пока раунд идёт, загадка не
  отдаётся и зрителю: иначе ответ просто выкрикнули бы игрокам. После итога
  зритель видит ответ, портрет персонажа и список раундов.
- **Занять место в дуэли** — если комната ещё ждёт второго игрока, зритель
  может стать им прямо из наблюдения, не возвращаясь к началу.
- **Участник** по своей же ссылке (или после обновления страницы) попадает
  сразу в дуэль: сервер помечает его как `member` в ответе наблюдения, и
  выбор ему не показывается.

Наблюдение требует входа в аккаунт, как и сама игра, но **участником комнаты
быть не обязательно** — в этом и смысл: роль выбирается на одной и той же
ссылке.

Ссылка-приглашение несёт адрес сервера в параметре `srv` (путь зависит от того,
где живут игры: на витрине он короткий):

```
https://amrgames.ru/narutodle/?srv=https://ai-parnik.ru&room=N2UY
```

При заходе адрес подставляется в настройки подключения автоматически
(цепочка из раздела «Страница миниигр /games»: ссылка → `greenhouse.games.conn.v1`
→ `greenhouse.state.v1`), поэтому и приглашённый, и зритель попадают
прямо в комнату. Если адреса в ссылке нет, берутся свои сохранённые настройки,
а если и их нет — настройки панели теплицы; вводить адрес вручную не нужно.
**API-ключ в ссылку не попадает** — и не нужен: раздел `/api/games/*` пускает
по аккаунту, а ключ в адресе тут же утёк бы вместе со ссылкой.

Комнаты живут в памяти сервера два часа и перезапуск не переживают (партии
короткие); чужая таблица попыток не отдаётся игрокам до итога раунда, загадка
не попадает в ответы API до конца раунда никому, кроме итогового состояния.
Действия с комнатами ограничены по частоте отдельным счётчиком (30 в минуту
на адрес), чтобы короткий код нельзя было перебирать; опрос состояния и
наблюдения под этот счётчик не попадает, иначе игра и зрители быстро
упирались бы в лимит.

##### Третья игра: 87-0 — драфт по Counter-Strike

`front/games/csdraft/index.html` — драфт-рогалик в духе 322-0.app, но по CS:
собираете состав из реальных ростеров прошлых турниров и прогоняете его по
сетке мейджора. Игра одиночная, но идёт целиком на сервере: связь нужна, как
и остальным играм.

Как идёт прогон:

1. **Лобби** — сложность (сколько даётся рероллов), эпоха («Легенды 2013–2019»
   или «Новое время 2020–2026») и способ расстановки. Рядом — журнал своих
   прогонов и число составов в базе.
2. **Драфт** — предлагается «пак»: это состав одной команды на одном турнире —
   пять игроков с ролями и карты того маппула. Из пака берут **только одно**:
   либо одного игрока в пять слотов ролей (AWP, IGL, энтри, сапорт, луркер),
   либо одну карту в свой маппул — после выбора состав на выбор меняется сам.
   Реролл заменяет предложенный состав на другой. В ручном режиме после
   «Взять» игра спрашивает, в какую роль поставить игрока.
3. **Мейджор** — четыре стадии: групповой этап (Bo1), четвертьфинал (Bo3),
   полуфинал (Bo3) и финал (Bo5). Усилений у «87-0» нет: между стадиями ничего
   не выбирается, следующая стадия идёт сразу за победой. **Поражение
   заканчивает прогон** — пройти все четыре стадии и значит «87-0».

Что влияет на силу:

- **Игроки** — средний рейтинг состава. У игрока три оценки: AIM, CLUTCH
  и IMP; общий рейтинг считается как `0.45·AIM + 0.25·CLUTCH + 0.30·IMP`.
- **Роли** — игрок в своём амплуа даёт `+4`, в родственном `0`, совсем не
  в своём `−5`; кнопка «Расставить» подбирает лучший вариант перебором.
- **Сыгранность** — `+2.5` за каждого, кто играл в этом же составе на этом же
  турнире, `+1` за игрока из того же региона и `+1.5` за известную связку.
- **Свои карты** — на карте из своего маппула играется легче (`+3`).

Матчи симулируются по картам и раундам: до 16 побед, при 15:15 — овертаймы по
шесть раундов до четырёх побед (не больше трёх овертаймов). Исход детерминирован
зерном прогона, поэтому один и тот же состав играет одну и ту же сетку.

Прогоны живут в памяти процесса (TTL 24 часа, не больше 300 за раз) —
перезапуск сервера их теряет. **Журнал** каждого законченного прогона пишется в
базу (`csdraft_runs`): аккаунт, сложность, эпоха, состав с ролями, паки, счёт по
стадиям и итог. Свой журнал виден на странице игры, общий — в служебной консоли
(`GET /api/games/csdraft/matches?scope=all`, только `admin`).

Набор составов лежит в базе (`csdraft_packs`), а исходники — два файла данных,
которые при заливке объединяются. Выверенные вручную составы — в
[`backend/csdraft_data.py`](backend/csdraft_data.py); массовый набор участников
мейджоров — в [`backend/csdraft_majors.py`](backend/csdraft_majors.py)
(`EVENTS`: турнир, год, эпоха и составы команд). Совпадения по команде и турниру
решает ручной набор: он сильнее машинного.

В массовом наборе ники, команды и места — исторические данные, а оценки
AIM/CLUTCH/IMP считаются по правилу от места на турнире и роли игрока
(`PLACE_POWER`, `ROLE_SHIFT` в том же файле), поэтому числа повторяемы, но это
игровые оценки, а не статистика HLTV. Паки, в которых возможна неточность
(стендин, спорная роль, границы состава), помечены в файле комментарием
«проверить»: список собран по памяти и требует сверки с таблицами турниров.
Мейджоры после BLAST Austin 2025 и турниры 2026 года в набор не занесены — их
нужно добавить из таблиц, когда они будут под рукой: достаточно дописать событие
в `EVENTS`.

Править и просматривать набор удобнее скриптом:

```powershell
# что в базе: составы по эпохам, карты, роли
python backend/seed_csdraft.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse" --list

# проверить набор (составы на пять игроков, известные роли, нет повторов)
python backend/seed_csdraft.py --db data/greenhouse.sqlite3 --check

# обновить набор из файла данных или убрать неточный состав
python backend/seed_csdraft.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse"
python backend/seed_csdraft.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse" --remove titan-dhw2014
```

Оговорки, которые честнее написать прямо:

- **оценки AIM/CLUTCH/IMP — игровые**, а не официальная статистика. Они
  расставлены так, чтобы сильные составы своей эпохи были сильнее, а у игроков
  разных амплуа был смысл в драфте; в интерфейсе и в файле данных это сказано;
- ники игроков, названия команд и турниров — **исторические факты** и
  принадлежат их владельцам. Игра некоммерческая, не связана с Valve и не
  копирует оформление чужих сайтов;
- состав на турнире указан по основному амплуа игрока. Двое в паке могут делить
  одну роль — в драфте из-за этого и приходится кого-то ставить не в свою роль.

##### Четвёртая и пятая игры: 13-0 (Valorant) и 4-0 (Rocket League)

Две отдельные игры (`front/games/valorant/index.html` и `front/games/rl/index.html`),
движок у них **один** ([`backend/csdraft.py`](backend/csdraft.py)), а отличия
(роли, арены, стадии, усиления, правила розыгрыша площадки) собраны в реестре
[`backend/draft_games.py`](backend/draft_games.py), поэтому новая игра
добавляется конфигурацией, а не новым кодом.

- **13-0 (Valorant)**: состав из реальных команд VCT — дуэлист, инициатор,
  контроллер, часовой и флекс; карта играется до 13 побед, при 12:12 — овертаймы
  по два раунда до двух побед; финал Champions — Bo5. Набор составов: VCT
  Champions и Masters 2021–2024 (Acend, Gambit, Sentinels, LOUD, OpTic, FPX,
  Paper Rex, EG, Fnatic, EDG, Heretics, Gen.G).
- **4-0 (Rocket League)**: тройка из истории RLCS — атакующий, полузащитник и
  защитник; серии Bo5/Bo5/Bo7/Bo7, арена играется до трёх голов. Набор: Gale
  Force, Dignitas, Cloud9, Vitality, NRG (2017–2019) и BDS, G2, Moist,
  Vitality (2021–2024).

Разметка, стили и скрипт страниц общие: они лежат в `front/games/draft/`
(`index.html` — разметка, `draft.css` и `draft.js` — оформление и логика).
На витрине `/games/` у каждой игры **своя карточка**, поэтому в игру заходят
напрямую, а не через выбор игры. Страница `/games/draft/` осталась прямым
адресом на случай старых ссылок: там игра выбирается внутри и выбор

выбора игры на них скрыто, а в `localStorage` выбор не пишется. **При правке
разметки нужно поправить все три файла** — это отмечено комментарием в самих
страницах.

Страница сама берёт подписи из ответа сервера (`GET /api/games/draft/games`),
поэтому терминология у каждой игры своя: где-то «карты маппула», где-то «арены
пула». Правила прогона, журнал и рероллы — как у «87-0», а усиления между
стадиями есть только у этих игр: у «87-0» их нет. Адреса отличаются ключом
игры: `/api/games/draft/valorant/*` и `/api/games/draft/rl/*`
(у CS остался старый короткий адрес `/api/games/csdraft/*`). В базе паки всех
игр лежат в одной таблице `csdraft_packs`, а разделяет их колонка `game`.

##### Шестая игра: Рэп-хронология

`front/games/raporder/index.html` — игра про порядок треков русского рэпа.
В раунде пять треков **разных годов**, и их надо расставить от самого старого к
самому новому; очко даётся за каждый трек, вставший на своё место (0–5). Соло —
пять раундов подряд, игра на сумму очков; онлайн — комната по коду, где у всех
один и тот же раунд, три раунда и победа по выигранным раундам (в ничейном раунде
очко не достаётся никому).

Годы в раунде обязаны отличаться: иначе «правильный порядок» был бы
неоднозначным. Раунд кончается, когда ответили все (или вышло время); потом
показывается разбор с годами. Правильный порядок и годы не попадают в ответы API,
пока раунд не закончился.

Набор лежит в базе (`raporder_tracks`), исходник — в
[`backend/raporder_data.py`](backend/raporder_data.py), журнал партий —
в `raporder_matches` (режим, комната, счёт обоих, победитель, подробность).
Заходы и комнаты живут в памяти сервера (TTL 30 минут и 2 часа), как у остальных
игр.

**Текстов песен и аудио в игре нет и не будет**: игра про хронологию, а не про
слова. Хранятся только исполнитель, название и год. Годы стоит перепроверять —
часть дат проставлена по памяти (год альбома вместо года сингла или год
переиздания), поэтому набор правится на месте:

```powershell
# что в базе и сколько разных годов
python backend/seed_raporder.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse" --list

# проверить набор (пустые поля, повтор id, хватает ли разных годов)
python backend/seed_raporder.py --db data/greenhouse.sqlite3 --check

# поправить год на месте или убрать трек
python backend/seed_raporder.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse" --year krovostok-reka=2005
python backend/seed_raporder.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse" --remove старый-id
```

Исполнитель, название и год — факты из открытых источников и принадлежат их
авторам и правообладателям; игра некоммерческая.

##### Седьмая игра: 322-0 (драфт по Dota 2)

`front/games/dota322/` — фэнтези-драфт по Streamers Battle 13 в духе 322-0.app:
сначала собирается состав из пяти игроков в бюджет, потом каждому выдаётся герой,
и только затем играются стадии турнира.

- **Состав и бюджет.** Пул — 140 игроков Streamers Battle 13 со стоимостями
  из таблицы владельца сайта (10–95 очков). Состав — пять игроков, и сумма
  стоимостей не должна выйти за бюджет: в хардкоре это 300 очков (обычная игра —
  320, смёрф — 340). Игрока можно убрать из состава, и его стоимость вернётся.
- **Герои по позициям.** Каждому игроку выбирается герой, а позиция героя (1–5:
  Керри, Мидер, Офлейнер, Четвёрка, Пятёрка) становится позицией игрока: пять
  героев обязаны закрыть все пять позиций, повтор позиции или героя запрещён.
  Кнопка «Расставить героев» делает это автоматически: по одному лучшему герою
  на позицию, дорогому игроку — герой посильнее.
- **Сила состава.** `0,62 × стоимость игрока + 0,38 × оценка героя` в среднем по
  пятёрке, плюс надбавки: звёздный игрок (≥85) на сильном герое (≥88) даёт +4,
  дорогой игрок на слабом герое (≤80) — минус 3. Между стадиями предлагается
  усиление: по позиции (+4), тренер (+5), свежая мета (по +4 к каждому герою,
  то есть +1,52 к силе) и заготовки драфта.
- **Стадии.** Групповой этап (Bo1), четвертьфинал (Bo3), полуфинал (Bo3) и финал
  (Bo5); поражение заканчивает прогон. Соперник — случайный «микс» из того же
  пула, собранный под бюджет стадии (288/308/328/348 очков с поправкой на
  сложность), с героями из верхней половины позиции: сила растёт от стадии к
  стадии, поэтому слабый или недоукомплектованный состав вылетает сразу.
- **Журнал.** Итог каждого прогона уходит в общую таблицу `csdraft_runs`
  с `game = 'dota322'`: аккаунт, сложность, состав (`ник (Позиция, Герой)`),
  соперники по стадиям, счёт и стадия вылета.

Пул лежит в базе (`dotadraft_players`, `dotadraft_heroes`), исходник —
в [`backend/dotadraft_data.py`](backend/dotadraft_data.py); при пустых таблицах
сервер заливает набор сам. Стоимости правятся в файле данных или на месте:

```powershell
# что в базе: игроки по стоимости и герои по позициям
python backend/seed_dotadraft.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse" --list

# проверить набор (уникальные id, заполненные поля, герои на все позиции, бюджет)
python backend/seed_dotadraft.py --db data/greenhouse.sqlite3 --check

# обновить набор из файла данных, поправить стоимость или убрать игрока
python backend/seed_dotadraft.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse"
python backend/seed_dotadraft.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse" --cost dm=90
python backend/seed_dotadraft.py --db data/greenhouse.sqlite3 --remove-hero magnus
```

Стоимости игроков — из таблицы владельца сайта, оценки героев — игровые (они
влияют только на силу состава). Ники участников, Dota 2 и её герои —
исторические названия и товарные знаки их владельцев; игра некоммерческая.

##### Восьмая игра: Угадай песню за 10 секунд

`front/games/songguess/index.html` — быстрая игра на слух: звучит короткий
фрагмент, а на экране четыре названия песен. В отличие от «Аниме-сонглесса»,
где раунд идёт 20 секунд и угадывается аниме, здесь **жёсткий таймер на ответ** —
и это и есть выбор сложности: 5 секунд (блиц), 10 (обычная) или 15 (спокойная).

- **Тема** выбирается в лобби: аниме-опенинги, русский рэп, зарубежный хип-хоп.
  Набор — 126 песен ([`backend/songguess_data.py`](backend/songguess_data.py)).
- **Заход** — пять раундов. Фрагмент музыки — до пяти секунд; очки: 100 за верный
  ответ плюс до 100 за скорость (доля оставшегося времени). Промах или
  просроченный таймер — раунд потерян, очков нет. После раунда пять секунд
  разбора: видно название, исполнителя, год и откуда песня.
- **Итог** уходит в журнал `songguess_runs`: тема, таймер, число верных, очки
  и разбор по раундам. Свой журнал виден на странице игры, общий — в служебной
  консоли (`GET /api/games/songguess/matches?scope=all`, только `admin`).

Правильный вариант не показывается, пока раунд не закончился, а фрагмент отдаётся
отдельным адресом `/api/games/songguess/runs/<id>/clip?round=N` — по имени файла
песню тоже не угадать. Заходы живут в памяти процесса (TTL 30 минут, не больше
400 за раз), перезапуск сервера их теряет.

###### Записи песен добавляет владелец сайта

В репозитории есть **только справочные сведения** (тема, название, исполнитель,
год, сериал или источник) — сами записи защищены авторским правом. Песни лежат
в таблице `songguess_tracks`, а записи привязывает
[`backend/seed_songguess.py`](backend/seed_songguess.py); файлы копируются
в свой каталог `front/games/songguess/audio` (он не общий с «Аниме-сонглессом»):

```powershell
# справочный набор в базу и что из него уже можно играть
python backend/seed_songguess.py --dsn "postgresql://greenhouse:пароль@localhost:5432/greenhouse"
python backend/seed_songguess.py --dsn "..." --list

# свои записи: файлы копируются в front/games/songguess/audio и привязываются по имени
python backend/seed_songguess.py --dsn "..." --audio "C:\music" --category anime --map music.json

# или ссылкой, с точным местом фрагмента
python backend/seed_songguess.py --dsn "..." --url "anime-again=https://example.org/song.mp3"
python backend/seed_songguess.py --dsn "..." --start "anime-again=42" --length 5

# проверить набор или отвязать неудачную запись
python backend/seed_songguess.py --db data/greenhouse.sqlite3 --check
python backend/seed_songguess.py --dsn "..." --clear-audio anime-again
```

Повторный запуск обновляет справочные сведения и **не затирает** привязанные
записи, начало и длину фрагмента. Куда класть файлы и что нельзя выкладывать —
в [`front/games/songguess/audio/README.md`](front/games/songguess/audio/README.md).

**Тема играбельна, только если в ней не меньше четырёх песен с записью** — иначе
для раунда не хватит вариантов. Пока записей нет, карточка темы выключена, а
страница честно пишет, сколько записей не хватает и какой командой их добавить:
синтетических «заглушек» в игре нет.

Логин одновременно является и паролем: `X-Api-Token` нужен для «теплицы»,
`Authorization: Bearer` — для аккаунта. Их можно использовать вместе.

Разделы `/api/auth/*`, `/api/admin/*`, `/api/secret/*` и `/api/games/*`
работают **без** общего ключа: их закрывает аккаунт (`Bearer`). Так сделано
специально — иначе придётся класть ключ в ссылку-приглашение на дуэль,
а ссылки пересылают друзьям.

Раздел `/api/device/*` открывается **устройство-токеном** (заголовок
`X-Device-Token`): он принадлежит только домашнему агенту и не совпадает с
ключом панели — если сервер стоит на VPS, ключ панели лежит в браузере у
пользователей, и пускать им агента нельзя. Без `--device-remote` раздел закрыт
(404): сервер сам работает с платой и агент ему не нужен.

При заданном API-ключе любой из методов ниже требует заголовок
`X-Api-Token` (или `?token=...`), иначе вернётся `401`.

Пример:

```powershell
curl http://127.0.0.1:8000/api/state
curl -X POST http://127.0.0.1:8000/api/devices -H "Content-Type: application/json" -d "{\"zone_id\":3,\"device\":\"watering\",\"on\":true,\"seconds\":10}"
```

#### PostgreSQL и pgAdmin

Тот же сервер и тот же REST API умеют работать с **PostgreSQL** вместо файла
SQLite: состав таблиц и все запросы совпадают, но время хранится в `TIMESTAMPTZ`,
флаги — в `BOOLEAN`, а ключи — в `BIGSERIAL`. Ответы API при этом не меняются.

```powershell
# 1) драйвер (нужен только для режима PostgreSQL)
py -m pip install -r backend/requirements.txt

# 2) база и роль — один раз, из psql или pgAdmin → Query Tool
#    CREATE ROLE greenhouse LOGIN CREATEDB PASSWORD 'пароль';
#    CREATE DATABASE greenhouse OWNER greenhouse;

# 3) чтобы не вводить пароль каждый раз — строка в %APPDATA%\postgresql\pgpass.conf
#    localhost:5432:*:greenhouse:пароль
#    (формат: хост:порт:база:роль:пароль, * — любая база)

# 4) сервер на PostgreSQL
py backend/server.py --dsn "postgresql://greenhouse@localhost:5432/greenhouse"

# либо через переменную окружения, чтобы не указывать ключ каждый раз
$env:GREENHOUSE_DSN = "postgresql://greenhouse@localhost:5432/greenhouse"
py backend/server.py
```

Без `--dsn` (и без `GREENHOUSE_DSN`) сервер по-прежнему пишет в SQLite —
ничего переписывать не нужно. Пароль не хранится ни в репозитории, ни в командах:
его подхватывает `pgpass.conf` (если файла нет, сервер спросит пароль).

Схема создаётся автоматически при первом запуске, вручную её можно выполнить
из файла [`backend/schema_postgres.sql`](backend/schema_postgres.sql).

**Перенос уже накопленных данных из SQLite:**

```powershell
py backend/migrate_to_postgres.py --dsn "postgresql://greenhouse@localhost:5432/greenhouse"
py backend/migrate_to_postgres.py --dsn "..." --replace               # сначала очистить таблицы в PostgreSQL
py backend/migrate_to_postgres.py --dsn "..." --history-limit 5000    # только свежие показания
```

Скрипт копирует `zones`, `readings`, `zone_devices`, `settings`, `state`,
`logs`, а также аккаунты и связанное с ними — `users`, `auth_sessions`,
`user_states`, `secret_data`. Поэтому переезд не разлогинивает панель:
сессии и сохранённое состояние переезжают вместе с аккаунтами.
Повторный запуск можно делать без опаски — строки обновляются по ключу.

Чтобы перенести только часть таблиц (например, не трогая историю показаний,
которая уже накопилась в PostgreSQL), есть ключ `--only`:

```powershell
py backend/migrate_to_postgres.py --dsn "..." --only users,auth_sessions,user_states,secret_data
```

**Просмотр в pgAdmin:**

1. Правый клик на **Servers** → **Register → Server…**
2. Вкладка *General*: Name — «Теплица».
3. Вкладка *Connection*: Host — `localhost`, Port — `5432`,
   Maintenance database — `greenhouse`, Username — `greenhouse`, пароль роли
   (галочка *Save password* — чтобы не вводить каждый раз).
4. **Save** → `Databases → greenhouse → Schemas → public → Tables`.
5. Правый клик на таблице → **View/Edit Data → All Rows**.

Те же подключения можно загрузить разом из файла
[`pgadmin-servers.json`](pgadmin-servers.json): **File → Import Servers…** →
указать файл → **Import**.

**Чтобы добавить ещё одну базу или таблицу:**

* новая база — `CREATE DATABASE имя OWNER greenhouse;` и запуск сервера с её DSN;
* новая таблица — добавить операторы `CREATE TABLE` в
  [`backend/schema_postgres.sql`](backend/schema_postgres.sql), соответствующие
  запросы в [`backend/db_postgres.py`](backend/db_postgres.py) и (если нужно
  переносить данные) строку в `TRANSFERS` там же.

### 3. Датчики через Arduino

Прошивка: [`hardware/arduino/greenhouse_12zone/greenhouse_12zone.ino`](hardware/arduino/greenhouse_12zone/greenhouse_12zone.ino)

* 12 датчиков влажности через аналоговый мультиплексор **CD74HC4067**;
* температура/влажность воздуха — **DHT22**;
* уровень воды в баке — **HC-SR04**;
* управление — 2× **74HC595** (12 насосов + вентилятор + фитолампа).

Обмен — построчный JSON по Serial (115200 бод). Схема соединений и список
библиотек — в [`hardware/README.md`](hardware/README.md).

**Платы пока нет — это не проблема.** Если не указан `--serial`, сервер
включает встроенный **эмулятор**: физическая модель микроклимата 12 участков
(испарение, полив, нагрев, освещение от времени суток). Эмулятор полностью
повторяет протокол платы, поэтому переход на реальное железо сводится к
добавлению флага `--serial COM3`.

Порт занимает та программа, что стоит рядом с платой. Если сервер переехал на
VPS, `--serial` нужен не ему, а домашнему агенту
([`backend/device_agent.py`](backend/device_agent.py)): он читает плату и
отправляет показания серверу — см. «Бэкенд на VPS» ниже.

### 6. Публикация: панель на reg.ru, API и база — дома

Проверено по официальной документации reg.ru (help.reg.ru и приложение к оферте):
на shared-хостинге с ISPmanager **есть только MySQL, PostgreSQL нет**;
Python работает лишь как WSGI-приложение под Passenger (`passenger_wsgi.py`),
а суточный лимит CPU — 2,5–13 %, за превышение хостинг блокируется.
Поэтому бэкенд теплицы — с COM-портом Arduino, циклом автоматики и PostgreSQL —
остаётся на домашнем ПК, а на хостинг уезжает только статичная панель:

```
front/   →  https://ваш-домен.ru        (FTP 21 или SFTP 22, корень сайта)
backend  →  домашний ПК: PostgreSQL + Arduino, наружу через HTTPS-туннель
```

Порядок:

1. Загрузить содержимое папки `front/` в корень сайта
   (`/var/www/uXXXXXXX/data/www/<домен>/`): `index.html`, `css/`, `js/`,
   `icons/`, `manifest.webmanifest`, `service-worker.js`,
   `TriEblanaiPraktika/` (служебная страница).
   Панель должна лежать в корне — иначе service worker не получит нужную область
   видимости и приложение не установится.
2. В ISPmanager включить бесплатный **Let's Encrypt** и редирект HTTP→HTTPS.
3. Поднять туннель к домашнему серверу — его выдаёт Cloudflare Tunnel.
   Проще всего скриптом [`_run_public.ps1`](_run_public.ps1), он поднимает
   и сервер, и туннель, и печатает готовый адрес:

   ```powershell
   $env:GREENHOUSE_TOKEN = "длинный-секрет"          # ключ панели, обязателен
   $env:GREENHOUSE_DSN   = "postgresql://greenhouse@localhost:5432/greenhouse"
   $env:GREENHOUSE_ADMIN_PASSWORD = "пароль-админа"  # только для первого запуска
   powershell -ExecutionPolicy Bypass -File _run_public.ps1
   ```
   `GREENHOUSE_ADMIN_PASSWORD` нужен лишь один раз: пока в базе нет ни одного
   аккаунта, сервер создаёт `admin` с этим паролем. Без переменной пароль
   генерируется случайным и печатается в окне сервера — не пропустите его.

   Скрипт требует `cloudflared` (`winget install Cloudflare.cloudflared`),
   сохраняет адрес туннеля в `data/tunnel-url.txt` и печатает команду остановки.
   Туннель запускается в режиме `--protocol http2`: QUIC(UDP) часто режется
   домашним антивирусом или файрволом.

   Провайдеры периодически блокируют инфраструктуру туннелей (соединение до
   Cloudflare, ngrok и подобных рвётся на этапе TLS). Тогда туннель поднимается
   не с первой попытки — [`_tunnel_retry.ps1`](_tunnel_retry.ps1) пробует снова
   каждые несколько минут, а когда получается, держит туннель живым и обновляет
   `data/tunnel-url.txt`:

   ```powershell
   powershell -ExecutionPolicy Bypass -File _tunnel_retry.ps1 -IntervalSeconds 180 -MaxHours 6
   ```

   В некоторых сетях Cloudflare глушат иначе: канал регистрируется, процесс жив,
   обрывов в журнале нет, а запросы снаружи получают `530`. Тогда помогает
   обратный **SSH-туннель** через localhost.run — [`_tunnel_ssh.ps1`](_tunnel_ssh.ps1)
   (нужен системный VPN/TUN-режим, иначе сервер туннеля недоступен):

   ```powershell
   powershell -ExecutionPolicy Bypass -File _tunnel_ssh.ps1 -Port 8000 -MaxHours 12
   ```

   Скрипт по умолчанию подключается **по SSH-ключу** (`localhost.run`): тогда
   имя туннеля закрепляется за ключом и не меняется при переподключениях.
   Ключ берётся из `%USERPROFILE%\.ssh` (подойдёт обычный `id_rsa`), а его
   публичную часть нужно один раз добавить в аккаунт на
   <https://admin.localhost.run/> — без этого адрес не выдаётся вовсе, и тогда
   запускайте анонимный режим:

   ```powershell
   powershell -ExecutionPolicy Bypass -File _tunnel_ssh.ps1            # по ключу, адрес постоянный
   powershell -ExecutionPolicy Bypass -File _tunnel_ssh.ps1 -RemoteUserHost nokey@localhost.run
   ```

   Туннель работает **только пока запущен скрипт**: по умолчанию это одиночный
   режим — при обрыве скрипт сообщает об этом и завершается, ничего не
   перезапуская. Окно `ssh.exe` скрыто, поэтому поверх других программ ничего
   не всплывает. Для длительной демонстрации панели нужен `-KeepAlive`: тогда
   скрипт сам переподключается при обрыве. Остановить — отдельной командой:

   ```powershell
   powershell -ExecutionPolicy Bypass -File _tunnel_ssh.ps1 -KeepAlive   # с автоподключением
   powershell -ExecutionPolicy Bypass -File _tunnel_stop.ps1             # остановить туннель и сервер
   ```

   **Сервер теплицы скрипт держит сам.** Туннель без сервера ведёт в пустоту:
   запросы снаружи получают 502, а сайт «не открывается». Поэтому перед
   подключением и во время работы скрипт проверяет порт и, если сервера нет,
   поднимает `backend/server.py` заново — параметры подключения берутся из
   `-Dsn`/`-Token`, переменных окружения `GREENHOUSE_DSN`/`GREENHOUSE_TOKEN`
   или файлов `data/dsn.txt` и `data/api-key.txt`:

   ```powershell
   Set-Content data\dsn.txt 'postgresql://greenhouse:пароль@localhost:5432/greenhouse' -Encoding UTF8
   Set-Content data\api-key.txt 'ключ-панели' -Encoding UTF8
   ```

   Свой сервер, запущенный вручную, скрипт не трогает: процесс поднимается,
   только когда порт молчит. Запущенные им PID-ы лежат в `data/server.pid`, и
   `_tunnel_stop.ps1` останавливает их вместе с туннелем (`-KeepServer` —
   оставить сервер, `-NoServer` — не следить за ним вовсе).
   Важно: скрипт живёт, пока открыт его процесс. Перезагрузка компьютера или
   закрытие окна останавливает и туннель, и сервер — тогда сайт недоступен, пока
   всё не запустят снова (см. «Свой сервер вместо домашнего компьютера» ниже).

   В анонимном режиме localhost.run выдаёт случайный адрес вида `<hex>.lhr.life`
   и обрывает сессию каждые несколько минут, поэтому при каждом переподключении
   адрес меняется — скрипт сам записывает новый в `data/tunnel-url.txt` и сразу
   публикует его на сайте (см. «Текущий адрес API на сайте» ниже), так что в
   панели его указывать заново не нужно. Актуальный PID туннеля лежит в
   `data/tunnel.pid` (нужен скрипту остановки).

   **Постоянный адрес на своём домене** даёт платный тариф Custom Domain
   (9 $/мес при годовой оплате): в админке добавляется домен, в DNS прописывается
   TXT `_lhr.<домен>` для подтверждения и CNAME `<поддомен>` → `cd.localhost.run`,
   после чего туннель поднимается на своём имени:

   ```powershell
   ssh -R api.ai-parnik.ru:80:localhost:8000 plan@localhost.run
   ```

   Оба скрипта считают успехом не запись в журнале, а реальный ответ туннеля,
   и переподключаются при обрыве. Адрес из `data/tunnel-url.txt` действует, пока
   работает окно скрипта.

4. Панель на вкладке «Режим» → «Подключение к серверу» берёт **адрес API и
   ключ** сама (из `games/api-address.json`, опубликованного на сайте). Если
   адрес пришлось задать вручную — указать адрес из `data/tunnel-url.txt` и
   **API-ключ**, нажать «Подключиться», после чего войти в аккаунт (логин
   `admin` и пароль из шага 3).

#### Текущий адрес API на сайте

Поддомен быстрого туннеля меняется при каждом перезапуске, поэтому адрес
публикуется в файле `games/api-address.json` на сайте — оттуда его подхватывают
панель, витрина `/games/` и страницы игр. Публикует его скрипт
[`_publish_address.py`](_publish_address.py): он берёт адрес из
`data/tunnel-url.txt`, проверяет, что тот отвечает, кладёт файл на хостинг по
SFTP и перечитывает его с сайта для проверки.

Вместе с адресом в файл попадает **ключ панели**, поэтому браузеру не нужно
спрашивать его у пользователя: панель и витрина подставляют ключ сами, если
своего у них нет или если сервер не принял старый. Ключ берётся из переменной
`GH_API_KEY` или из файла `data/api-key.txt` (каталог `data/` в репозиторий не
попадает, а сам файл на сайте в репозиторий не выгружается — см. `.gitignore`).

```powershell
$env:GH_HOST_PASSWORD = 'пароль хостинга'
python _publish_address.py                     # адрес и ключ
python _publish_address.py --dry-run           # показать, что будет записано
python _publish_address.py --no-key            # только адрес, без ключа
python _publish_address.py --address https://abc.lhr.life
```

> **Внимание.** Файл на сайте открыт всем посетителям, поэтому ключ в нём может
> прочитать любой: панель и управление теплицей перестают быть закрытыми. Если
> это недопустимо, публикуйте файл без ключа (`--no-key`, убрать
> `data/api-key.txt`) — тогда ключ вводится в браузере один раз и запоминается
> там.

Пароль хостинга в репозитории не хранится — он читается из переменной окружения
или из файла `data/host-password.txt` (каталог `data/` в репозиторий не попадает):

```powershell
Set-Content data\host-password.txt 'пароль хостинга' -Encoding UTF8
```

Скрипты туннеля [`_tunnel_ssh.ps1`](_tunnel_ssh.ps1) и
[`_tunnel_retry.ps1`](_tunnel_retry.ps1) вызывают его сами после поднятия
туннеля: с заданным паролем адрес обновляется автоматически, без
него шаг просто пропускается с предупреждением. Нужен `paramiko`
(см. [`backend/requirements.txt`](backend/requirements.txt)).

Файл не кэшируется (правило для `.json` в [`front/.htaccess`](front/.htaccess)) и
не хранится в репозитории: он кладётся сразу на хостинг, поэтому устаревшая
копия не может попасть в следующую выгрузку.

**Постоянный адрес.** Быстрый туннель без аккаунта Cloudflare каждый раз получает
новое имя вида `https://<случайное-имя>.trycloudflare.com`, поэтому после
перезапуска адрес в панели нужно менять. Постоянный адрес даёт **именованный
туннель**, но для него домен должен быть переведён на NS-серверы Cloudflare
(на reg.ru это смена NS в личном кабинете, DNS-зону придётся перенести) — это
самостоятельный шаг, который лучше делать осознанно. CNAME `api.ai-parnik.ru`
на быстрый туннель не поможет: Cloudflare отвечает только на своё случайное имя.

**Демонстрация «здесь и сейчас»:** пока домашний ПК включён и запущен
`_run_public.ps1`, панель на `ai-parnik.ru` полностью рабочая. Как только ПК
выключается, панель переходит в демо-режим — данные в ней становятся местной
симуляцией, а не показаниями теплицы.

Ограничения, о которых стоит помнить:

* адрес API обязан быть **https** — иначе браузер заблокирует запросы
  как mixed content (на http-сайте панель останется в демо-режиме);
* **без API-ключа публиковать сервер нельзя** — команды насосам и вентиляции
  сможет отдать любой, кто узнает адрес;
* **панель закрыта входом**, а служебная страница `/TriEblanaiPraktika` видна
  всем, кто знает её адрес (изменения в ней — только под администратором);
* пока домашний ПК выключен, панель работает в демо-режиме;
* ключ панель хранит в `localStorage` браузера, поэтому на чужом устройстве
  его лучше не вводить. Токен входа тоже лежит в `localStorage` — на общем
  компьютере выходите из аккаунта кнопкой **⎋**.

#### Обновление панели на хостинге

nginx отдаёт `.js` и `.css` с кэшем на 45 дней, а `.html` и `.webmanifest` — через
Apache. Поэтому заголовки задаёт файл [`front/.htaccess`](front/.htaccess): он
добавляет манифесту тип `application/manifest+json` (без него браузер не
предложит установку и не включит приложение), запрещает кэшировать сам HTML и
`games/api-address.json` — иначе браузер подставил бы адрес прошлого туннеля.

Скрипты и стили идут мимо `.htaccess`, поэтому их ссылки версионируются:
`css/main.css?v=N` и `js/app.js?v=N` в [`front/index.html`](front/index.html),
то же `N` в `css/main.css?v=N` на страницах
[`front/games/index.html`](front/games/index.html),
[`front/games/narutodle/index.html`](front/games/narutodle/index.html),
[`front/games/animesongless/index.html`](front/games/animesongless/index.html),
[`front/games/csdraft/index.html`](front/games/csdraft/index.html),
[`front/games/draft/index.html`](front/games/draft/index.html),
[`front/games/valorant/index.html`](front/games/valorant/index.html),
[`front/games/rl/index.html`](front/games/rl/index.html),
[`front/games/raporder/index.html`](front/games/raporder/index.html),
[`front/games/dota322/index.html`](front/games/dota322/index.html) и
[`front/games/songguess/index.html`](front/games/songguess/index.html),
а также в ссылках на общие для драфт-игр `draft.css` и `draft.js`
в [`front/games/draft/index.html`](front/games/draft/index.html),
[`front/games/valorant/index.html`](front/games/valorant/index.html) и
[`front/games/rl/index.html`](front/games/rl/index.html),
в `ASSET_VERSION` в [`front/js/app.js`](front/js/app.js) и в `VERSION`
в [`front/service-worker.js`](front/service-worker.js). При выпуске новой версии
поднимите `N` во всех этих файлах и загрузите файлы заново — обновление дойдёт
и до тех, у кого панель уже установлена.

Сами страницы service worker всегда запрашивает из сети: в кэш они попадают
только как запасной вариант для офлайна, поэтому свежая вёрстка видна сразу
после обновления, даже если приложение уже установлено.

### 7. Бэкенд на VPS: сайт работает без домашнего ПК

Схема из предыдущего раздела зависит от дома: выключили ПК, оборвался туннель,
сменился поддомен — панель и игры недоступны. Если перенести сервер и базу на
VPS, сайт работает круглосуточно, адрес API постоянный, а туннель не нужен
вовсе. Дома остаётся только плата с агентом:

```
Дом:   Arduino ──COM-порт── device_agent.py ─────── HTTPS ──────┐
                                                                ↓
VPS:                        server.py + PostgreSQL  ◀────────────┘
                                     ▲
Сайты: ai-parnik.ru (панель) ────────┘  панель, игры, API и статика
       amrgames.ru (витрина игр) ────── nginx раздаёт front/games,
                                       а запросы /api/ уходят сюда же
```

Агент раз в 2 секунды отправляет показания (`POST /api/device/sync`) и в ответ
получает команды, которые нажали в панели или выдала автоматика; применив их к
плате, он подтверждает результат (`POST /api/device/ack`).

#### Быстрый путь: одна команда с Windows

Ставить вручную не обязательно: из папки проекта на своём компьютере

```powershell
# живая база уже PostgreSQL: данные переносятся дампом, снятым здесь же
powershell -ExecutionPolicy Bypass -File _upload_to_vps.ps1 -Server <IP сервера> `
    -Domain ai-parnik.ru -Email me@example.com -PgDump

# или из SQLite, если база ещё файловая
powershell -ExecutionPolicy Bypass -File _upload_to_vps.ps1 -Server <IP сервера> `
    -Domain ai-parnik.ru -Email me@example.com -Sqlite data\greenhouse.sqlite3

# панель теплицы и витрина мини-игр двумя доменами на одном сервере
powershell -ExecutionPolicy Bypass -File _upload_to_vps.ps1 -Server <IP сервера> `
    -Domain ai-parnik.ru -GamesDomain amrgames.ru -Email me@example.com -PgDump
```

[`_upload_to_vps.ps1`](_upload_to_vps.ps1) соберёт архив проекта (без `.git`,
`.venv` и баз), скопирует его по scp, распакует в `/opt/greenhouse` и запустит
там [`_setup_vps.sh`](_setup_vps.sh): пакеты, роль и база PostgreSQL, окружение
Python, служба `systemd`, nginx, сертификат Let's Encrypt и перенос данных.
Секреты установщик генерирует сам, печатает один раз и сохраняет в
`/etc/greenhouse.env` (права 600) — при повторном запуске они не меняются.

Перенос данных бывает двух видов, и оба проверены на живой базе:

* **`-PgDump`** — для рабочей базы PostgreSQL. Скрипт снимает дамп
  (`pg_dump --clean --if-exists`), копирует его в `/tmp` и передаёт установщику
  `--dump`: тот восстанавливает таблицы от имени `postgres` в базу `greenhouse`.
  Переносятся аккаунты, журналы матчей, персонажи вместе с портретами и всё
  остальное; повторный запуск перезаливает таблицы, а не удваивает записи.
  Источник берётся из `-Dsn`, переменной `GREENHOUSE_DSN` или файла
  `data\dsn.txt`; путь к `pg_dump.exe` при необходимости задаёт `-PgDumpPath`
  (по умолчанию скрипт ищет его в `PATH` и в `C:\Program Files\PostgreSQL`).
* **`-Sqlite`** — для файловой базы: она копируется на сервер, и установщик
  наполняет PostgreSQL через [`backend/migrate_to_postgres.py`](backend/migrate_to_postgres.py).

Если передать оба ключа, восстанавливается дамп, а SQLite пропускается: иначе
одни и те же записи попали бы в базу дважды.

Ничего не меняя на сервере, можно посмотреть план: добавьте `-DryRun` (дамп
снимается и на этой стадии — так сразу видно, что источник отвечает).
Повторный запуск того же скрипта обновляет код на сервере (`-SkipApt -NoNginx`,
если не нужно трогать пакеты и nginx).

Ключи `_upload_to_vps.ps1`: `-Server` (обязательный), `-User` (по умолчанию
`root`), `-Key` (путь к SSH-ключу; без него ssh спросит пароль),
`-Domain` (можно несколько через запятую), `-GamesDomain` (домен витрины игр на
том же сервере; тоже можно несколько), `-Email`, `-PgDump`, `-Dsn`,
`-PgDumpPath`, `-Sqlite`, `-RemoteRoot`, `-Port`, `-SkipApt`, `-NoNginx`,
`-DryRun`.

#### Витрина игр на своём домене

`-GamesDomain` (в [`_setup_vps.sh`](_setup_vps.sh) — `--games-domain`) заводит
второй сайт на том же сервере. Nginx раздаёт его прямо из каталога
`front/games`, поэтому игры живут по коротким адресам:

```
https://amrgames.ru/             витрина: список мини-игр
https://amrgames.ru/narutodle/   страница игры; так же csdraft, dota322,
                                 valorant, rl, raporder, songguess,
                                 animesongless
https://amrgames.ru/api/...      тот же сервер теплицы (обратный прокси)
```

Сертификат на домены витрины выпускает тот же запуск: повторный прогон
расширяет уже имеющийся сертификат (`--expand`), а если перевыпуск не
потребовался, TLS всё равно переустанавливается в заново записанный конфиг
nginx.

Страницы витрины общие с проектом: тот же `front/games`, те же стили, тот же
код игр. Панель теплицы, служебная страница и сам API на домене витрины не
появляются — например, `/TriEblanaiPraktika` там отвечает `404`. Адрес API
страницы игр ищут как обычно: файл `api-address.json` лежит в самом каталоге
витрины, поэтому страница игры читает его как `/api-address.json` и получает
адрес панели вместе с ключом. Чужой домен серверу не мешает: в
[`backend/server.py`](backend/server.py) включён `Access-Control-Allow-Origin: *`.
Если файла нет, игра работает со своим доменом — `/api/` витрины nginx
перенаправляет серверу теплицы.

Раздел игр на домене панели при этом закрыт: `/games/` там отвечает `404`, так
что игры живут в одном месте и файлы записей не раздаются с двух доменов. Без
`--games-domain` (например, если витрину ещё не завели) раздел `/games/`
остаётся на панели как был.

Исключение — ровно один путь: `/games/api-address.json` на домене панели
остаётся доступным, чтобы браузеры со старым адресом туннеля смогли переехать
на новый сервер (раздел «Текущий адрес API на сайте»).

Копию файла из репозитория [`_upload_to_vps.ps1`](_upload_to_vps.ps1) не
выгружает: там может лежать устаревший адрес туннеля, и он увёл бы игры на
несуществующий сервер. На сервере файл публикуется отдельно и остаётся
рабочим — именно из него страницы игр берут ключ `X-Api-Token`.

Так как страницы общие, на домене витрины nginx подменяет в них название сайта и
запрет индексации (`sub_filter`), не трогая сами файлы:

| На панели, `ai-parnik.ru` | На витрине, `amrgames.ru` |
|---|---|
| вкладка `Игровая комната · Умная AI-Теплица` | вкладка `Игровая комната · AmrGames` |
| `<h1>Игровая комната</h1>` | `<h1>AmrGames</h1>` |
| `noindex, nofollow` — поисковикам закрыто | `index, follow` — поисковикам открыто |
| стрелка «назад» ведёт к панели | стрелка ведёт на `https://ai-parnik.ru/` |

Правила лежат в конфиге витрины (`/etc/nginx/sites-available/amrgames`) и
записываются установщиком: если в шапке витрины
([`front/games/index.html`](front/games/index.html)) поменять тексты, поправить
нужно и там — конфиг при повторном запуске перезаписывается, так что правки
вносятся в [`_setup_vps.sh`](_setup_vps.sh).

Витрина работает и при выключенном сервере теплицы: страницы отдаёт nginx, а
игры в этом случае показывают «нужна связь». `sub_filter` есть в nginx из
штатных пакетов Debian и Ubuntu; если его вдруг нет, установщик предупредит, и
витрина просто останется под прежним названием.

#### Порядок переезда с домашнего компьютера

1. Заказать VPS (см. требования ниже) и узнать его IP; при заказе выбрать
   Ubuntu 24.04 или Debian 13.
2. Прописать DNS: A-записи домена (и `api.`, если API будет на поддомене), а
   если витрина игр будет на своём домене — то и её (`amrgames.ru`, а если
   витрина нужна и по `www.` — то и `www.amrgames.ru`). Без этого не выпустится
   сертификат.
3. Остановить туннель, чтобы данные не менялись во время переноса:
   `powershell -ExecutionPolicy Bypass -File _tunnel_stop.ps1`.
4. Выполнить команду из «Быстрого пути» выше с `-PgDump`.
5. Проверить сайт по домену: панель должна открыться, вход — аккаунтом,
   который уже есть в базе (перенос сохраняет пароли).
6. Дома оставить только агента:
   `python backend/device_agent.py --server https://<домен> --device-token <токен> --serial COM3`
   (токен напечатан установщиком и лежит в `/etc/greenhouse.env`).
7. На reg.ru после этого достаточно одного адреса: `https://<домен>` —
   `games/api-address.json` и публикация туннеля больше не нужны. Витрина игр
   на своём домене тоже обходится без файла: её страницы берут адрес API у того
   же домена.

Дальше — подробный разбор тех же шагов: он пригодится, если сервер уже настроен
или что-то нужно поправить руками.

#### Что понадобится

* **VPS:** 1–2 ядра, 1–2 ГБ RAM, 10–20 ГБ диска, Ubuntu 24.04 или Debian 13.
  Сервер написан на стандартной библиотеке Python, база — PostgreSQL, поэтому
  такой конфигурации хватает с запасом: на VPS уезжают только API, база и
  статика.
* **Поддомен для API,** например `api.ai-parnik.ru`: A-запись на IP сервера.
  Он нужен для HTTPS, а HTTPS здесь обязателен — панель отправляет API-ключ и
  токены входа, агент — свой устройство-токен.
* **Дома:** ПК или мини-ПК с Arduino и Python 3.11+ (там уже лежит репозиторий).

#### Порядок

1. Подготовить сервер:

```bash
sudo apt update && sudo apt install -y python3 python3-venv postgresql nginx
python3 --version    # нужен 3.11 или новее: Ubuntu 24.04 даёт 3.12, Debian 13 — 3.13
sudo -u postgres psql -c "CREATE ROLE greenhouse LOGIN PASSWORD 'пароль';"
sudo -u postgres psql -c "CREATE DATABASE greenhouse OWNER greenhouse;"
```

Если в системе только 3.10 или старее (например, Ubuntu 22.04), поставьте
отдельный интерпретатор и создавайте окружение им:
`sudo apt install -y python3.12 python3.12-venv`, а дальше `python3.12 -m venv .venv`.

2. Разместить код и зависимости:

```bash
sudo mkdir -p /opt/greenhouse && sudo chown "$USER" /opt/greenhouse
git clone <адрес репозитория> /opt/greenhouse && cd /opt/greenhouse
python3 -m venv .venv && .venv/bin/pip install -r backend/requirements.txt
```

3. Перенести данные: `python backend/migrate_to_postgres.py --dsn "postgresql://greenhouse@localhost:5432/greenhouse"`
   (из копии `data/greenhouse.sqlite3`) либо наполнить базу заново через
   [`seed_narutodle.py`](backend/seed_narutodle.py) и
   [`seed_songless.py`](backend/seed_songless.py). Записи опенингов для
   «Аниме-сонглесса» — обычные файлы в
   [`front/games/animesongless/audio`](front/games/animesongless/audio), их
   нужно скопировать вместе с кодом.

4. Завести секреты (файл только для root и службы):

```bash
sudo install -m 600 /dev/null /etc/greenhouse.env
```

```
GREENHOUSE_DSN=postgresql://greenhouse:пароль@localhost:5432/greenhouse
GREENHOUSE_TOKEN=ключ-панели
GREENHOUSE_DEVICE_TOKEN=токен-агента
GREENHOUSE_ADMIN_PASSWORD=пароль-админа
```

5. Поставить службу сервера — `/etc/systemd/system/greenhouse.service`:

```ini
[Unit]
Description=Умная AI-Теплица: API, база и панель
After=network.target postgresql.service

[Service]
User=greenhouse
WorkingDirectory=/opt/greenhouse
EnvironmentFile=/etc/greenhouse.env
ExecStart=/opt/greenhouse/.venv/bin/python backend/server.py --host 127.0.0.1 --port 8000 --device-remote
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl enable --now greenhouse
journalctl -u greenhouse -n 30 --no-pager   # что написал сервер при запуске
```

Ключ `--device-remote` переводит сервер в режим агента: платы рядом нет,
показания приносит агент, команды уходят через очередь. Без `--device-token`
сервер в этом режиме не запустится — раздел агента должен быть закрыт своим
секретом, а не ключом панели (он лежит в браузере у пользователей).

6. Закрыть HTTPS: nginx как обратный прокси на `127.0.0.1:8000` и сертификат
   Let's Encrypt (`certbot`). Минимальный конфиг:

```nginx
server {
    server_name api.ai-parnik.ru;
    client_max_body_size 8m;             # фрагменты записей для «Аниме-сонглесса»
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

7. Запустить агента дома (на компьютере, где воткнута Arduino):

```powershell
python backend/device_agent.py --server https://api.ai-parnik.ru `
    --device-token <токен-агента> --serial COM3
```

Без `--serial` агент работает эмулятором — так удобно проверить связку до того,
как плата будет подключена. Автозапуск: задача в Планировщике заданий Windows
(«При входе в систему») или служба `systemd` на мини-ПК. COM-порт занимает
**только агент**: не запускайте на этом же компьютере сервер с `--serial`, иначе
порт окажется занят.

8. Указать адрес в панели: раздел «Режим» → `https://api.ai-parnik.ru` (и один
   раз опубликовать его для всех страниц: `python _publish_address.py --address https://api.ai-parnik.ru`).
   Адрес постоянный, поэтому повторять публикацию при каждом запуске больше
   не нужно — в отличие от туннеля из предыдущего раздела.

   Если панель раздаётся тем же сервером (в `--domain` указан и основной домен),
   ничего указывать не нужно: страница берёт адрес API с того же домена, а файл
   `games/api-address.json` и шаред-хостинг reg.ru вообще становятся не нужны.

#### Проверка

```bash
curl https://api.ai-parnik.ru/api/health  -H "X-Api-Token: <ключ панели>"
curl https://api.ai-parnik.ru/api/arduino -H "X-Api-Token: <ключ панели>"
```

Во втором ответе ждём `"mode": "remote"` и `"connected": true`. В панели в шапке
появится «Сервер · агент · Arduino», а в журнале — «Домашний агент на связи
(Arduino COM3)».

#### Если дом пропал

* показания перестают приходить, в шапке панели — «агент не на связи»,
  в журнале — «Домашний агент не выходит на связь 60 с»;
* команды, нажатые в панели, ждут агента, но выполняются только свежими: через
  2 минуты они закрываются с пометкой «просрочена» — полив через час после
  нажатия кнопки опаснее пропуска команды;
* автоматика не решает по устаревшим цифрам: она ждёт связи (в журнале
  «Автоматика ждёт связи с платой») и продолжает работу, когда агент вернулся;
* вход в аккаунт, Narutodle и «Аниме-сонглесс» работают всё это время — они
  живут на сервере и от дома не зависят.

Совсем без домашнего ПК можно обойтись, только если сама плата выйдет в сеть:
Wi-Fi-контроллер (ESP32) обращается к серверу теми же запросами, что и агент.
Это доработка прошивки, а не сервера: устройство-токен и раздел `/api/device/*`
для неё уже готовы.
